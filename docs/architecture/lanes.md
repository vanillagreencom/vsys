# Lanes and processes

Covers: src/model/lanes.ts src/model/naming.ts src/model/launcher.ts src/model/launcher.test.ts src/model/scopes.ts src/model/alerts.ts src/model/alerts.test.ts src/model/types.ts src/collect/procs.ts src/collect/tmux.ts src/collect/io.ts src/collect/cgroups.ts src/model/lanes.test.ts src/collect/tmux.test.ts src/collect/collector.test.ts

A lane is a watched scope, or a group an agent or a resource alarm made worth watching. The collector reads the processes; the model derives the lane, its name, its launch trail and the alert rules that fire on it. [agent-tools.md](agent-tools.md) owns which processes are agent tools.

## Boundaries

- `unitLabel()` in `src/model/naming.ts` is the only place a systemd unit name becomes a name a screen shows. It drops the `app-` launcher prefix, the unit suffix and the generated field systemd adds for uniqueness, and decodes `\xNN` escapes.
- `distinctNames()` in `src/model/naming.ts` is the only rule for names that repeat, and its one caller is Resources. Lanes do not use it: a lane name is never added to, and two lanes resolving to one name are told apart by the process id column beside them.
- `laneText()` in `src/model/naming.ts` names a lane in prose, where there is no column to carry the process id: the name, then `PID` and the process leading it, or the name alone for a lane leading none.
- A lane name joins the configured parts in the configured order and leaves out a part with no value. `pane` is still accepted as a part so a stored config keeps loading, but it composes nothing.
- A tmux pane id such as `%9` is unique only within one server, so the lane keeps it as the handle `tmux switch-client -t` takes and never as a name. One `tmux list-panes` per sample resolves every lane at once into a `session:window.pane` address. Every tmux read runs through `spawnText()` in `src/collect/io.ts`, bounded by `tmuxTimeoutMs` so a wedged server costs one call rather than every future sample, and the call's exit status is returned unjudged; the kernel log search shares `spawnText()`, bounded by its own `kernelLogTimeoutMs`, because journalctl's exit 1 is an answer.
- `isPaneId` decides whether a value is `%N`, which settles two things: that it can be looked up in the pane map, and that as a target it names itself without one. A reader who configured an address instead already has what they would type, so it stands as the address and carries no window name, which only the server holds.
- A handle is resolved only against the server it belongs to. The lane carries the `TMUX` value its own shell exported, and a handle whose server is known to differ resolves to nothing rather than naming a stranger's pane.
- One pane on that server is vsys's own, the one it draws in, and `ownPaneMark()` answers one of three things about every lane: its pane is that one, its pane is not, or vsys cannot tell. What it guards is which pane a command reaches, and `capture-pane` and `switch-client` are spawned in vsys's own environment, so a target naming vsys's own pane reaches it whatever server handed the string out. A lane known to be on another server is answered `no`, because `elsewhere` stops it earlier and leaves it neither read nor offered a switch.
- A lane's target is what `paneName()` reads from the configured pane-variable list, `VSYS_PANE` first and `TMUX_PANE` after it. `targetPanes()` in `src/collect/tmux.ts` is the only place such a target becomes the panes it names, and the mark above rests on it rather than on how a reader spelled the target. tmux takes several spellings of one pane: `vsys:2.1` is the address the map holds, `vsys:build.1` names the window by its name, `vsys:2` leaves the pane to tmux, `vsys:build.%9` puts the handle in the pane component, where tmux resolves it whatever window stands beside it, and a leading `=` forces the exact match every comparison there already makes. A handle is read in the digits tmux prints, because `%009` and `%9` are one pane to tmux while the map is keyed by tmux's own unpadded output. The answer is a set because a target with no pane index names every pane of its window and only the server knows which of them tmux would pick. Matching is exact, so a name tmux would match as a pattern or a prefix names nothing here, and neither does a window part tmux reads as a selector rather than a name, such as a bare `+`, which reaches the next window while some window may also carry `+` as its literal name. A dotted target has two readings and tmux picks between them on the window part alone: where that part names a window the server holds, tmux stays in it and resolves the pane component there, a selector such as `{last}` or `top` or, for anything it does not know, that window's active pane; only where no such window exists does it retry the whole rest as one name. So a pane component that is neither an index nor a handle names nothing here whenever the window part beside it is a window the map holds, and the retry is what keeps a window named `my.app` resolving. Naming nothing is never read as naming some other pane.
- Only `no` permits a read, a switch or a copied command, and the three answers exist so that the one vsys cannot give is not read as that one. A set leaving vsys's own pane out is `no`, but only where the map holds vsys's own pane or the target is a handle, which is compared against vsys's own handle and needs no map: `no` is the one answer the map has to have spoken for, and a read that came back without vsys's own row settles nothing about the panes beside it. A set holding vsys's own pane alone is `yes`. Everything else is `unknown`: a pane read that failed, a spelling the map could not resolve, a read that named other panes but never vsys's own, or a window target holding vsys's own pane beside others. The last two are settled instead by the handle tmux exported into the lane's own pane, read from `TMUX_PANE` alone: a lane whose own shell is the pane vsys draws in is `yes`. That read stands with no map at all, but only because `src/collect/procs.ts` names `TMUX_PANE` in the environment allow-list itself rather than inheriting it from the pane-variable setting, which a reader may narrow. A handle a lane carries as its target is settled without the map too, because it names itself, so a failed read costs a reader the terminals it cannot decide rather than every terminal on the machine. A vsys running outside tmux draws in no pane, so every lane is answered `no`.
- What `yes` costs is a lane whose target vsys could not resolve but whose own shell sits in the pane vsys draws in, and a lane on an unknown server whose target collides with vsys's own: each is told vsys draws in it, which need not be true of the pane its command would have reached. What `unknown` costs is one terminal a reader could have read. Both are the safe answers, because the capture either message replaces would have drawn vsys's own screen.
- `sliceCompared()` in `src/model/lanes.ts` decides whether agents are compared against the agent slice at all. Only a probe that found the slice absent or masked stops the comparison, since systemd never starts either. A slice vsys could not read and a sample recorded before the probe keep it, so a failed read never silences an escaped agent. Where the slice is absent or masked, every agent is a lane with its own group's resources, and none is escaped.
- `probeAgentSlice()` in `src/collect/capabilities.ts` reads the slice every sample, because systemd starts a slice when the first unit is placed in it. A group of the slice's name anywhere in the sample's tree is the slice. Otherwise the path systemd gives the name decides: `slicePath()` nests a dashed name in the slice it prefixes. Where that path does not exist, a unit file or drop-in directory for the slice in the user manager's unit directories makes it present all the same ([D009](../decisions/D009-agent-slice-unit-file.md)), so a defined slice nothing has started yet still holds agents to it. The first directory in the user manager's order that holds a unit file decides, as it does for systemd, and a unit file there that resolves to `/dev/null` reads `masked`, a failure of its own: Settings says the slice is masked and offers no line, because `systemctl` refuses to set a property on a masked unit. Otherwise only a slice with no unit file and no drop-in is absent, and a path that exists but cannot be read leaves it unknown.
- `launcherKnown()` in `src/model/launcher.ts` decides whether a card may speak of a launcher: the slice is present and `capMarkers` names at least one marker. A sample recorded before the slice probe counts the slice present, as `sliceCompared()` does, so its card reads as it did when it was recorded. Without both, a missing marker says nothing about how an agent started, so the unconfined card states the slice limit and gives no launcher conclusion.
- `scopeMain()` in `src/model/scopes.ts` picks a scope's main process: the oldest member whose parent sits outside the scope.
- `launcherTrail()` in `src/model/launcher.ts` reads the facts of one process and states no prose: the scope it names is the unit name, not a phrase. `launcherCopy()` writes the prose a card draws, and is the only place that writes it: it groups the trails by the four facts a sentence states, keyed on the whole cgroup path, and gives each group a conclusion and an ancestor clause the card can drop on its own, taken from a member whose ancestors the sample still holds. `launcherTally()` writes the one line a card too narrow for a sentence can hold: every group counted under its own conclusion.

## Invariants

1. An escaped agent is a configured tool outside the configured agent slice, on a machine that has the slice, decided once by `escaped()`. `src/collect/collector.test.ts` checks an escaped agent against an inherited cap, and two agents with the slice present and absent; `src/model/lanes.test.ts` tables the comparison for a present, unreadable, unrecorded, absent and masked slice; `src/collect/capabilities.test.ts` tables the probe.
2. The environment of an escaped agent is read from that agent, not from its scope's main process, and scope launch metadata belongs to the scope's main process. `src/collect/collector.test.ts` checks an agent child of a pane shell and a wrapper with an agent child.
3. A launcher trail states the ancestors and their cgroups, the confinement markers and any PATH prefix, and names a repeated neighbour in the chain once. Markers with the wrong cgroup mean a shadowed launcher, their absence a bare launch, and an unreadable environment neither. `src/model/launcher.test.ts` checks all three.
4. One sentence covers every process agreeing on all four facts it states: the conclusion, the cgroup, the markers set on them and the PATH entries ahead of the login shell's own. It names the markers once, the scope once with the count of processes in it, and the ancestors once for an example process it names by PID. `src/model/launcher.test.ts` groups six processes in one scope, ten over two, and pairs differing only by marker set, only by PATH prefix, and only by the slice above a scope of one unit name.
5. A lane name joins the configured parts in the configured order and leaves out a part with no value. `src/model/naming.test.ts` checks the order; `src/model/lanes.test.ts` checks two accounts in one worktree and a lane naming no account.
6. No lane name carries a pane address or a disambiguator, and no unit name reaches a screen carrying a `\xNN` escape, the `app-` prefix or a `.scope` suffix. `src/model/naming.test.ts` checks the unit forms; `src/model/lanes.test.ts` checks that a name holds no separator the server gave it.
7. No two resource groups in one sample render the same name, and hiding the idle rows never renames one. `src/ui/resources.test.tsx` checks the separation and the filtered list.
8. Per-lane page cache, I/O rates, CPU share and cgroup weight stay unknown when the kernel did not report them, and an unread cgroup tree leaves the effective memory cap unknown rather than unlimited. `src/model/lanes.test.ts` checks a group with no counters and a lane with no covering group.
9. A cgroup limit file holds a number or the word max, so a file that could not be read leaves the effective cap known only when every covering ancestor was read. `src/collect/collector.test.ts` removes an ancestor's `memory.max`.
10. A blocked lane counts its tasks in uninterruptible wait and names storage or memory by the higher stall share, naming neither when the pressure is unknown. `src/model/lanes.test.ts` checks both resources and unknown pressure.
11. Process environment caching uses the PID with its start time, so a reused PID is a different process. `src/collect/collector.test.ts` exercises PID reuse and environment selection.
12. When a PID appears in sibling scope lists, its process membership file selects the row. `src/collect/collector.test.ts` checks that fallback.
13. Each new escaped agent emits its own alert even inside an already alarmed scope, and every rule clears before it rearms. `src/model/alerts.test.ts` checks process identity and rearming.
14. One tmux read resolves every lane's pane whatever the number of lanes, and a server that stops answering costs the addresses rather than the sample. `src/collect/collector.test.ts` counts the reads and fails one on purpose.
15. A configured pane address is a target tmux accepts rather than one vsys refuses, and a pane on another server resolves to nothing. `src/model/lanes.test.ts` and `src/collect/tmux.test.ts` check both, including a restarted server on one socket path.
16. Whether a lane holds the pane vsys draws in is answered `yes`, `no` or `unknown`, and only `no` permits a read, a switch or a copied command. The answer is the set of panes the lane's target names, so every spelling tmux takes of one pane earns one answer; a target the map could not resolve, and one it resolved under a read that never named vsys's own pane, are both `unknown` rather than `no`, and the handle in the lane's own `TMUX_PANE` settles it as `yes` when that shell is the pane vsys draws in. A lane known to be on another server is answered `no`, because the command the answer guards runs against vsys's own server and `elsewhere` stops that lane earlier. `src/collect/tmux.test.ts` tables each spelling against a map holding a split window and a window name reused in another session, and checks what one read carries; `src/model/lanes.test.ts` tables the answer for each spelling, for the targets that stay undecided and for the shell that settles them, tables both forms against vsys's own server, another server and no server, and checks a pane that is not vsys's in either form, a vsys outside tmux, and a failed read answering all three; `src/collect/collector.test.ts` checks a sample whose read answered and one whose read failed.
17. The unconfined card names a launcher only where the slice is present and confinement markers are configured. `src/ui/attention.test.ts` checks a present slice with and without markers, an unreadable slice and a sample recorded before the probe.
18. A tmux read that stalls is killed within `tmuxTimeoutMs` rather than blocking every future sample. `src/collect/tmux.test.ts` kills a real stalled child and checks the deadline holds.
