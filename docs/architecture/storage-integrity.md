# Storage integrity

Covers: src/collect/btrfs.ts src/collect/btrfs.test.ts src/collect/errors.ts src/collect/kernel-log.ts src/collect/kernel-log.test.ts src/collect/scrub.test.ts src/model/integrity.ts src/model/integrity.test.ts src/ui/integrity.ts scripts/scrub_reporter_test.py

Storage answers two questions per filesystem: is its data damaged, and when was it last read end to end. Three sources answer them. A check report says what a completed scrub found. The error counter and the kernel log each record a failed read when one happens. Filesystem, device and mount collection are in [storage](storage.md). The scrub reporter that writes a check report, and the report format, are in [the scrub reporter](scrub-reporter.md).

## Boundaries

- The filesystem, not the mount and not the device, is the unit of integrity. `volumesByDevice` in `src/model/integrity.ts` forms that group, and the cause ladder, the Storage line and the drill-down all read the one `integrity()` reading per group.
- The error counter counts reads that failed their checksum, not damaged files. It cannot move while nothing reads the damage, so a flat counter is never on its own a statement that the filesystem is sound. Only a completed check is.
- The time of a filesystem's last counter growth is kept in `errorMemoryPath`, outside the history window and outside the process. A growth time a write never landed lives only in this process, so the filesystem reads as unknown until one does. A counter reading zero after a reboot is a new baseline, never a repair. A write folds in the file as it stands, so two vsys processes watching one host keep the later growth time rather than the one that renamed last.
- A check that corrected every error it found left no damage behind. Corrected errors still raise a report card; they are not a damaged filesystem.
- The last check comes only from a report, and the collector remembers the last one that finished across a later report that did not. The reporter keeps one report per filesystem, so a scrub that stops early overwrites the report that proved the filesystem sound; `finishedScrub` in `StorageCollector` (`src/collect/btrfs.ts`) keeps each filesystem's last finished start time, in process memory, and only a later finished report moves it forward. `integrity()` falls back to it for `checkAge` whenever the current report is not itself finished. The last new error is the newer of the counter's last growth and the kernel log's last failed read, and the Storage line names the source of each time. A report read the whole filesystem. The counter and the log saw only the reads that happened, and the counter only while a vsys process watched it.

## The kernel log

- Btrfs logs every data read that fails its checksum as `csum failed root R ino I`. `KernelLog` in `src/collect/kernel-log.ts` reads those lines from `journalctl --output=json`, searched with `--grep`, so no helper is needed.
- The `kernel-log` capability searches for one kernel message from this boot, once at start. An answer with none means this user cannot read the system journal. A collector whose probe failed never searches.
- The message text is kernel prose, not an interface. It stands in for the `error_stats` counters under `/sys/fs/btrfs`, which give a count with no inode and no time it failed, and the reporter's `unable to fixup` lines stand in for `btrfs scrub status`, which gives counts with no address and, on btrfs-progs v7.1, no JSON form. A rewording leaves the lines unmatched: the log then names no failure, and a report lists fewer addresses than it counts, which Storage shows as unnamed damage.
- The first search reads every boot the journal holds. Each later search starts after the cursor the last one ended on. The dashboard's first sample and a plain `--once` pay it; a collector built for a settings change resumes from the cursor. `--once --summary` skips the log, as it skips scratch, so its integrity reads the counter alone.
- A search that fails records a source error naming `journalctl`, and the failures earlier searches read still stand. The log reads as unread only where no search has completed.
- A logged failure is a dated reading even where the counter's record of past growth could not be read, so the line gives its time and source.
- A device name holds for one boot. A failure is matched to its filesystem through the `first mount of filesystem` line its own boot logged for that device. A failure from this boot with no such line is matched through this boot's sysfs. A failure from an earlier boot with no such line is left out.
- Resolving an inode to a path needs root. A failure the kernel logged after the last finished check shows as an inode in a subvolume. A check that finished later read the filesystem end to end and covers it.
- `csumFailures` holds the newest 64 inodes per filesystem. Null means the log was not read, which is never a log of none.

## Invariants

1. A report is matched to its filesystem by the UUID it carries, and its damaged-file list holds only paths still on disk, so a removed file leaves the list. `src/collect/btrfs.test.ts` removes one of an address's two names and reads the list back.
2. A report with no damaged-file section lists no files rather than none, and a field it omits stays unread. `src/collect/scrub.test.ts` checks both formats and a reworded header.
3. The first reading of a counter above zero establishes a baseline and claims no error time; later growth records its time and size, and a counter reset moves the baseline without erasing them. `src/collect/errors.test.ts` checks all three, and `src/collect/btrfs.test.ts` reads the time back from a second collector.
4. No integrity state but `healthy` and `checking` reads as untroubled, and a filesystem that was never checked, whose output could not be read, or whose counter is unreadable is never `healthy`. A check that stopped early, or a report gone from disk, is `healthy` only where a finished check is remembered, that remembered check found no damage, and nothing has grown or logged since; with no such memory it is `unknown`, and a remembered check that found damage is `damaged`, never `healthy` or `stale`, whatever the current report says or whether it exists at all. `src/model/integrity.test.ts` pins one row per state and a row per memory outcome, damage included.
5. Every file a report names is listed as possibly damaged, with every name its address carries, and no screen offers a command that removes one: on some kernels the logged block start names no file exactly. `src/model/integrity.test.ts` checks what each address names; `src/ui/integrity.test.ts` reads the words; `src/ui/storage-screen.test.tsx` copies nothing from a damaged filesystem and shows the sentence only while a file is listed; `src/ui/attention.test.ts` checks that the damage card tells no reader to remove a file.
6. A report that cannot be read stays a report: the row and its problem card remain rather than the file reading as absent. `src/collect/btrfs.test.ts` makes one unreadable and reads the row back.
7. A reading vsys could not take never becomes a reading of none: output that could not be read names no damaged file, and a record of past growth that failed to load leaves the state unknown rather than healthy, and is never overwritten by this process's own baselines. `src/model/integrity.test.ts` checks both states; `src/collect/errors.test.ts` checks the refusal to overwrite.
8. Each source answers on its own, and no source alone makes a filesystem healthy. With both, the newer error speaks, and a check that finished after a logged failure covers it. With reports only, the log reads as unread. With the kernel log only, a logged failure still dates the last new error and names its inode. With neither, the filesystem was never checked. `src/model/integrity.test.ts` holds one row per combination; `src/ui/integrity.test.ts` reads the source each line names; `src/ui/attention.test.ts` checks that the new-errors card tells neither source's error from before the last check.
9. A logged failure belongs to the filesystem its own boot mounted on that device, an earlier boot's failure with no mount line is left out, and a search that failed to parse is asked again from the same cursor. `src/collect/kernel-log.test.ts` renames a device across two boots and checks each.
10. A kernel log the probe could not search is never searched, and a search that fails names `journalctl`. The reading is unread only where no search has completed; invariant 14 holds what a later failure keeps. `src/collect/collector.test.ts` counts the searches; `src/collect/kernel-log.test.ts` checks the failure.
11. A report the reporter writes parses, through `parseScrub`, to the fields it carries; it lists only names proved to be of the damaged inode, drops another filesystem's address, never writes free space, a no-extent answer included, and leaves nothing vsys reads when stopped part way. A kernel log or a device list it cannot read leaves no damaged-file section. The installer installs under vsys's own names, migrates an old report into the persistent directory without overwriting one there, and installs nothing when the scrub unit is missing or a download fails. `scripts/scrub_reporter_test.py` runs both against stub system commands, and checks that the drop-in, the tmpfiles line and the default `scrubDir` name one directory.
12. A hidden file in the report directory is not a report, and an address marked not resolved reaches the sample as damage with no path. `src/collect/btrfs.test.ts` places a half-written report beside a complete one; `src/collect/scrub.test.ts` parses the mark.
13. Blocks the check counted beyond the listed addresses, and addresses not resolved, are damage no file covers: the Storage words count them beside the listed files, the damage card says the listed files are not all of the damage, and an empty list under a counted block is never free space. `src/model/integrity.test.ts` counts both; `src/ui/integrity.test.ts` and `src/ui/attention.test.ts` read the words.
14. A failed search keeps the failures earlier searches read, beside a `journalctl` source error; a search that matched nothing is an answer; the search pattern keeps the lines the parser reads; and the summary path never searches. A collector handed the log resumes its cursor, and `createCollector()` hands on the log the replaced collector held. `src/collect/kernel-log.test.ts` and `src/collect/collector.test.ts` check each.
15. The report directory is listed once per sample, asynchronously, so a reporter installed while vsys runs ends the offer at the next sample. `src/collect/collector.test.ts` creates the directory between two samples and fails a synchronous listing on the sample path; `src/ui/storage-screen.test.tsx` checks that an unreadable directory gets no offer and that a pinned sample still copies the line.
16. A name that differs from a healthy file's by an end space, or one the report cannot carry exactly, is never listed. `scripts/scrub_reporter_test.py` checks the reporter, including an inode with no name, a stderr warning and the `scrub: ` wording; `src/collect/btrfs.test.ts` reads a report whose last line ends in a space; `src/collect/scrub.test.ts` checks each name the text cannot carry.
17. A journalctl search that stalls is never left blocking every future sample: `spawnText()` sends SIGTERM at `kernelLogTimeoutMs`, then SIGKILL after a further `killGraceMs` for a child still running, which also bounds one that ignores SIGTERM. `src/collect/io.test.ts` kills a real SIGTERM-resistant child and checks the escalation.
18. A scrub that stops early, a report gone from disk, or a finished report that moved backward in time (a restored older report), never erases the memory of an earlier one that finished, its outcome included: `integrity()` treats a finished report as authoritative only when its own `startedAt` is no older than the remembered check's, and otherwise defers to that memory exactly as it does for a stopped-early report. `checkAge`, the state ladder's new-errors and damaged/healthy/stale evaluation, and the new-errors card's last-check age all keep naming the last finished report's age and damage state, and only a later finished report moves that memory forward. `scrubFoundDamage()` in `src/collect/btrfs.ts` is the one rule for whether a finished scrub's own numbers count as damage, and both the live report and a remembered one are judged by it, so a check that is only remembered reads no differently from one still live. The ladder judges `never-checked` against whether any finished check is on record at all, current or remembered, never against whether the current report is itself null or finished, so a remembered check keeps a filesystem out of `never-checked` and lets it read `healthy` or `stale` exactly as it would with that report still live — unless the remembered check found damage, which reads `damaged` instead and never `healthy` or `stale`, whatever the current report says. A kernel-log failure dated before the remembered check is already covered by it and is excluded from `logged` the same way a failure before a live finished report is. The memory is this process's own and survives a settings save rebuilding the collector, the same way the kernel log's cursor does, through `FinishedScrubMemory` (`src/collect/btrfs.ts`): `createCollector()` hands the replacement the replaced collector's own instance rather than a copy, so a scrub still finishing on the predecessor when the replacement is built, and found damaged only after that handoff, still lands in the one memory both collectors read. `src/collect/btrfs.test.ts` overwrites a finished report with one that stops early, reads the memory back, checks a stale replayed report never moves it backward, and checks a damaged outcome survives the same way a clean one does; `src/model/integrity.test.ts` checks the state and age `integrity()` derives from it, including a stopped-early report, one gone entirely, a remembered damaged check that a later stopped-early or missing report must not clear, a finished report that started before the remembered check and must not outrank it, and a logged failure on each side of the remembered time; `src/ui/attention.test.ts` checks the new-errors card still names that age rather than saying no check has ever run; `src/collect/collector.test.ts` checks a settings-rebuilt collector, built the way `Session.configure()` builds one, keeps the memory through the real `Collector.lastFinishedScrub` getter, and that a finish landing on the predecessor only after the rebuild still reaches the replacement because the two share that one `FinishedScrubMemory` rather than each holding a copy.
19. A `damaged` state reached only through a remembered check, its current report stopped early, gone, or itself finished but older than the remembered check, carries no address data: `damageCounts()` returns every count null rather than zero, which is the reading a report that actually named none would give, and the damage card tells the reader its last report naming the damage is no longer available instead of claiming the damage sits in free space or a deleted file. `src/model/integrity.test.ts` checks `damageCounts()` against a remembered-only damaged state; `src/ui/attention.test.ts` checks the card's words and its next step, both for a stopped-early report and one gone entirely.
