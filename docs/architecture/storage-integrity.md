# Storage integrity

Covers: src/collect/btrfs.ts src/collect/btrfs.test.ts src/collect/errors.ts src/collect/errors.test.ts src/collect/scrub.test.ts src/model/integrity.ts src/model/integrity.test.ts src/ui/integrity.ts scripts/scrub_reporter_test.py

Storage answers two questions per filesystem: is its data damaged, and when was it last read end to end. Three sources answer them. A check report says what a completed scrub found. The error counter and the kernel log each record a failed read when one happens. Filesystem, device and mount collection are in [storage](storage.md). The scrub reporter that writes a check report, and the report format, are in [the scrub reporter](scrub-reporter.md). How vsys searches the kernel log is in [the kernel log](kernel-log.md). Invariants 14 to 16, on the remembered finished check and on scrub coverage, are in [storage check memory](storage-check-memory.md).

## Boundaries

- The filesystem, not the mount and not the device, is the unit of integrity. `volumesByDevice` in `src/model/integrity.ts` forms that group, and the cause ladder, the Storage line and the drill-down all read the one `integrity()` reading per group.
- The error counter counts reads that failed their checksum, not damaged files. It cannot move while nothing reads the damage, so a flat counter is never on its own a statement that the filesystem is sound. Only a completed check is.
- The time of a filesystem's last counter growth, its size and the time of the reading it was measured from are kept in `errorMemoryPath`, outside the history window and outside the process. A growth time a write never landed lives only in this process, so the filesystem reads as unknown until one does. A counter reading zero after a reboot is a new baseline, never a repair. A write folds in the file as it stands, so two vsys processes watching one host keep the later growth time rather than the one that renamed last.
- A check that corrected every error it found left no damage behind. Corrected errors still raise a report card; they are not a damaged filesystem. The kernel counts every checksum mismatch a scrub finds, so the counter grows during the scrub, and vsys dates that growth at the next sample, which comes after the scrub ended when no vsys process sampled during it. A process holds every reading it takes, so where it took the reading before that sample, that reading bounds the growth from below to one sample interval. It writes only a changed counter, so the reading on disk can be far older than the last one taken: growth after a reading from disk has no lower bound, and the sample that saw it bounds it instead. `scrubCoverage()` in `src/collect/btrfs.ts` is the one rule for what a finished check accounts for: its end at its start plus `Duration`, and its `Corrected` plus `Uncorrectable`. `integrity()` covers growth whose bound came no later than that end and which is no larger than that count. The bound is written with the growth, so covered growth stays covered across a restart. Growth measured against the reading on disk keeps that reading's time instead. The kernel adds one to the counter per checksum error a scrub counts, so while nothing reset the counter since a reading taken before the scrub started, growth from it holds the report's whole `Error summary` csum count and any later error makes it larger: `integrity()` covers it only at that count. A reset vsys did not see, such as `btrfs device stats -z`, followed by exactly that many new failures reads covered; a readable kernel log still dates them after the check. Growth from a reading saved after the scrub started, or against no readable csum count, reads as new errors until the next scrub. Only the size of the last growth is remembered, so a read failure that grew the counter during the same scrub can be covered with it.
- The last check comes only from a report, and the collector remembers the last one that finished across a later report that did not. The reporter keeps one report per filesystem, so a scrub that stops early overwrites the report that proved the filesystem sound; `finishedScrub` in `StorageCollector` (`src/collect/btrfs.ts`) keeps each filesystem's last finished start time, in process memory, and only a later finished report moves it forward. `integrity()` falls back to it for `checkAge` whenever the current report is not itself finished. The last new error is the newer of the counter's last growth and the kernel log's last failed read, and the Storage line names the source of each time. A report read the whole filesystem. The counter and the log saw only the reads that happened, and the counter only while a vsys process watched it.

## Invariants

1. A report is matched to its filesystem by the UUID it carries, and its damaged-file list holds only paths still on disk, so a removed file leaves the list. `src/collect/btrfs.test.ts` removes one of an address's two names and reads the list back.
2. A report with no damaged-file section lists no files rather than none, and a field it omits stays unread. `src/collect/scrub.test.ts` checks both formats and a reworded header.
3. The first reading of a counter above zero establishes a baseline and claims no error time; later growth records its time, its size and the time of the reading before it, and a counter reset moves the baseline without erasing them. `src/collect/errors.test.ts` checks all three, and `src/collect/btrfs.test.ts` reads the time back from a second collector.
4. No integrity state but `healthy` and `checking` reads as untroubled, and a filesystem that was never checked, whose output could not be read, or whose counter is unreadable is never `healthy`. A check that stopped early, or a report gone from disk, is `healthy` only where a finished check is remembered, that remembered check found no damage, and nothing has grown or logged since; with no such memory it is `unknown`, and a remembered check that found damage is `damaged`, never `healthy` or `stale`, whatever the current report says or whether it exists at all. `src/model/integrity.test.ts` pins one row per state and a row per memory outcome, damage included.
5. Every file a report names is listed as possibly damaged, with every name its address carries, and no screen offers a command that removes one: on some kernels the logged block start names no file exactly. `src/model/integrity.test.ts` checks what each address names; `src/ui/integrity.test.ts` reads the words; `src/ui/storage-screen.test.tsx` copies nothing from a damaged filesystem and shows the sentence only while a file is listed; `src/ui/attention.test.ts` checks that the damage card tells no reader to remove a file.
6. A report that cannot be read stays a report: the row and its problem card remain rather than the file reading as absent. `src/collect/btrfs.test.ts` makes one unreadable and reads the row back.
7. A reading vsys could not take never becomes a reading of none: output that could not be read names no damaged file, and a record of past growth that failed to load leaves the state unknown rather than healthy, and is never overwritten by this process's own baselines. `src/model/integrity.test.ts` checks both states; `src/collect/errors.test.ts` checks the refusal to overwrite.
8. Each source answers on its own, and no source alone makes a filesystem healthy. With both, the newer error speaks, and a check that finished after a logged failure covers it. With reports only, the log reads as unread. With the kernel log only, a logged failure still dates the last new error and names its inode. With neither, the filesystem was never checked. `src/model/integrity.test.ts` holds one row per combination; `src/ui/integrity.test.ts` reads the source each line names; `src/ui/attention.test.ts` checks that the new-errors card tells neither source's error from before the last check.
9. A report the reporter writes parses, through `parseScrub`, to the fields it carries; it lists only names proved to be of the damaged inode, drops another filesystem's address, never writes free space, a no-extent answer included, and leaves nothing vsys reads when stopped part way. A kernel log or a device list it cannot read leaves no damaged-file section. The installer installs under vsys's own names, migrates an old report into the persistent directory without overwriting one there, and installs nothing when the scrub unit is missing or a download fails. `scripts/scrub_reporter_test.py` runs both against stub system commands, and checks that the drop-in, the tmpfiles line and the default `scrubDir` name one directory.
10. A hidden file in the report directory is not a report, and an address marked not resolved reaches the sample as damage with no path. `src/collect/btrfs.test.ts` places a half-written report beside a complete one; `src/collect/scrub.test.ts` parses the mark.
11. Blocks the check counted beyond the listed addresses, and addresses not resolved, are damage no file covers: the Storage words count them beside the listed files, the damage card says the listed files are not all of the damage, and an empty list under a counted block is never free space. `src/model/integrity.test.ts` counts both; `src/ui/integrity.test.ts` and `src/ui/attention.test.ts` read the words.
12. The report directory is listed once per sample, asynchronously, so a reporter installed while vsys runs ends the offer at the next sample. `src/collect/collector.test.ts` creates the directory between two samples and fails a synchronous listing on the sample path; `src/ui/storage-screen.test.tsx` checks that an unreadable directory gets no offer and that a pinned sample still copies the line.
13. A name that differs from a healthy file's by an end space, or one the report cannot carry exactly, is never listed. `scripts/scrub_reporter_test.py` checks the reporter, including an inode with no name, a stderr warning and the `scrub: ` wording; `src/collect/btrfs.test.ts` reads a report whose last line ends in a space; `src/collect/scrub.test.ts` checks each name the text cannot carry.
