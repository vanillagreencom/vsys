# Settings and the runtime

Covers: src/config/ src/collect/settings.ts src/collect/capabilities.ts src/collect/capabilities.test.ts src/runtime.ts src/runtime.test.ts src/ui/settings-screen.tsx src/ui/settings.ts src/main.ts src/ui/App.tsx src/ui/screen.tsx src/ui/screen.test.tsx

Settings are validated before they reach a running dashboard. The runtime replaces the collector, the history store or neither, depending on which settings changed. A capability is a system interface a reading needs, probed once at start, except the three re-read each sample.

## Boundaries

- Every host-specific name is configuration: the agent and desktop slices, the excluded argv patterns, the confinement cap markers, the compiler, linker and cache names, and the environment variables carrying the account, the pane, the window title and the build token pool. Desktop app install paths are configured in the shared agent-tool data and its overlay, not in `config.toml`; [agent-tools.md](agent-tools.md) owns how collection reads them.
- `collectionKeys` in `src/collect/settings.ts` is the only declaration of what collection reads, and `CollectionConfig` is the type every collection entry point takes. Reading an undeclared setting fails the type check rather than leaving the collector stale.
- Display settings and notification rules are deliberately not collection settings, because rebuilding the collector discards the counters and alert state a sample compares against.
- `Session` in `src/runtime.ts` owns one scheduler for collection and settings changes, so samples never overlap and a failed settings write leaves the active source and history usable.
- `xdgHome()` in `src/config/xdg.ts` is the one reading of an XDG base directory. A variable that is empty or not an absolute path falls back to its default under the home directory, as the base directory specification and systemd both require. The settings file is `configPath()` under `XDG_CONFIG_HOME`, the history database and error memory defaults sit under `XDG_STATE_HOME`, and the unit directories the agent slice probe reads sit under `XDG_CONFIG_HOME` and `XDG_DATA_HOME`. `xdgPath()` resolves the settings file and the state directory: where the variable points away from the home default and only the home default holds the path, the home default stays in use, so an existing install keeps its settings, history and error memory until the reader moves them. The state directory is resolved once per process, because history holds its database open there and a save compares against that default. The settings file is resolved again at each save, so a save writes where the next start reads. The agent-tool overlay stays at `~/.config/vsys/agent-tools.json` whatever `XDG_CONFIG_HOME` holds, because the warden reads it there.
- `choices` in `src/config/config.ts` is the one table both the picker and `validate` read, so a value a reader can pick is a value that saves.
- `saveConfig()` writes only settings that differ from the layered defaults. `Session` reloads the current agent-tool overlay before a Settings save, and rebases agent-program edits on that current overlay. It refuses an agent-program edit when a hand-written `config.toml` pin omits a shipped name, because the overlay cannot encode removals. A failed config save rolls back that overlay only when it still matches the body this save wrote. A diverging hand-written `config.toml` pin remains a dashboard override. D006 records the save rule. `sameValue()` in `src/config/config.ts` is the one judgement of whether a setting holds its default, and a save writes only the settings that differ. Storage reads the same judgement: a scratch list equal to the shipped list is the default, whether `config.toml` omits it or pins it unchanged, and any other list is the reader's, as [storage](storage.md) states.
- `settingInfo` in `src/ui/settings.ts` holds one entry per setting: the label that fits the list column, the sentence the drill-down shows, and the unit a stored number is written in. The list shows the value in that unit; the editor opens the stored value.
- Settings also names the file an edit here would save to, in a row of its own. `settingsFileInfo` in `src/ui/settings.ts` holds that row's label and sentence; the row sits outside `settingInfo` and `settingGroups` because the path is not a stored setting, the way the sources row sits outside them. `src/main.ts` builds the one resolver the startup load, every later sample and every save all call; `Session` in `src/runtime.ts` holds that resolver and calls it again on each sample's frame, the same call `configure()` makes before a save, and publishes that save's resolved value to the screen before it writes. The displayed row and the file a save writes to can never diverge, even when the reader moves the settings file and saves before the next sample.
- The capability probe reads each interface once at start, so an interface cannot change between ticks. Three answers are re-read each sample: whether a tmux server answers and whether the agent slice exists, because this is a dashboard for agents that start after it, and whether the scrub report directory exists, because the reader creates it by installing the reporter vsys offers. That last answer comes from the storage collection's asynchronous listing of the directory, never a second, synchronous read. [lanes.md](lanes.md) owns what the agent slice probe decides.
- A replaced collector hands its replacement the build cache reader and the kernel log, so a reading measured since vsys started, and the log's cursor, survive the change.
- A kernel log journalctl refused to search in its own words is a refusal, and its reason names journalctl rather than group membership; silence with no message is a journal this user cannot see.
- `capabilityOffer()` in `src/ui/settings.ts` is the one place a missing capability offers a line to supply it, except the scrub reporter's install, which `reporterOffer()` owns because Storage offers the same line. An absent agent slice offers `systemctl --user set-property` with the `MemoryHigh` and `MemoryMax` values of the warden's slice template, `warden/systemd/agents.slice`; the template's other limits are not part of the line. A slice that is defined but not running is present, so it is offered nothing, and a masked slice is offered nothing because `systemctl` refuses to set a property on a masked unit. The line is text to copy; vsys never runs it.
- The scrub reports row on Settings offers the scrub reporter's install line under the same rule as Storage, and the copy key on that row copies it. A Settings row that offers no line copies nothing.
- vsys reads system state unless write mode is on. A remediation command is text to copy; write mode additionally lets a confirmed Freeze, Thaw or Stop reach the lane's scope.

## Invariants

1. Every host-specific name ships a systemd user-session default, and write mode ships off. `src/config/config.test.ts` checks both.
2. An unknown setting, a wrong type, a duplicate list entry, a relative path where an absolute one is required and a threshold out of range each stop loading. `src/config/config.test.ts` checks invalid settings and malformed TOML.
3. Saving settings through a file link preserves the link and updates its target. `src/config/config.test.ts` checks the target contents.
4. A saved collection setting rebuilds the source before the next sample, and a display setting or a notification rule does not. `src/runtime.test.ts` checks all three.
5. A settings change waits for the in-flight source before sampling again, and hands the running source to its replacement. `src/runtime.test.ts` checks both.
6. A failed settings write leaves the active history and source usable. `src/runtime.test.ts` checks replacement failure.
7. A missing capability carries its source and a cause following what the probe met, so an unreadable or unparsable source is never called a missing interface, a tmux without a server is never called a missing tmux, and an `io.stat` at the session root is never taken for one in the groups below it while the root's `cgroup.subtree_control` leaves out `io`. `src/collect/capabilities.test.ts` checks the diagnoses; `src/ui/settings.test.ts` checks the words.
8. Every sample carries the capabilities probed when vsys started, except the three re-read each sample: whether a tmux server answers, the agent slice as this sample found it, and whether the scrub report directory exists. `src/collect/capabilities.test.ts` checks the probe, including a slice that appears after vsys starts; `src/collect/collector.test.ts` creates the scrub report directory between two samples, and checks that a sample lists it only through the storage read.
9. Every stored setting has a label, a sentence and, where it stores a number, a unit, and no label is wider than its column. `src/ui/settings.test.ts` derives the expected set from the defaults.
10. A stored value reads in the reader's unit rather than the stored one, and an interval under a second reads as itself rather than as zero. `src/ui/settings.test.ts` checks both.
11. Every setting sits in exactly one group, and no group names a stranger. `src/ui/settings-screen.test.tsx` derives the expected set from the defaults.
12. The Settings filter matches the stored name and the label the reader sees, so either spelling finds a row. `src/ui/settings-screen.test.tsx` checks a query only the labels carry.
13. What Enter does follows from the value the setting holds, decided once by `editorKind`. A boolean toggles with no editor, an enum offers its words, and everything else opens the text box. `src/ui/settings-screen.test.tsx` checks each kind from the keyboard.
14. A value the validator refuses is reported and never saved, a picker keeps its choice on the screen however long its list, search cannot open behind a picker, a click on another row leaves an open editor where it is, and a query leaves selected the row it matched or none. `src/ui/settings-screen.test.tsx` checks all five.
15. Settings reports the running program while a past sample is pinned, because the probe describes the program rather than the sample. The agent slice row is the per-sample exception: it reports the live sample, not the pinned one. `src/ui/settings-screen.test.tsx` checks both.
16. Write mode off refuses every lane action; on, each stands behind a confirmation naming the scope. A pinned sample refuses one whatever write mode says, because its scope name may belong to another lane by now. `src/ui/agent.test.tsx` checks all four.
17. A Settings save writes only changed keys, and an agent-program edit writes `~/.config/vsys/agent-tools.json` without pinning `agentTools` in `config.toml`. A pin that omits a shipped name refuses agent-program edits until the reader edits or removes the pin. A failed config save rolls back only the overlay body it wrote, so a newer overlay stays in place. `src/config/config.test.ts` checks the saved TOML and migration cases; `src/runtime.test.ts` checks stale overlay saves, pinned and unpinned Settings edits, unrelated saves over a diverging pin, pinned removal refusal, rollback after a config write failure, skipped rollback after a newer overlay and warden loader parity.
18. Of the agent slice states, only an absent slice offers a line that limits one, carrying the `MemoryHigh` and `MemoryMax` values the warden template sets, and the copy key copies it from that row and not from a row that offers nothing. A defined slice with no group yet, and a masked slice, are offered nothing. `src/ui/settings.test.ts` reads both values from the template and checks the masked slice; `src/collect/capabilities.test.ts` checks the defined slice; `src/ui/settings-screen.test.tsx` copies from the row and from another row.
19. The settings file follows `XDG_CONFIG_HOME`, and the history and error memory defaults follow `XDG_STATE_HOME`. With each variable unset, empty, relative or set to its home default, the paths stay `~/.config/vsys/config.toml` and `~/.local/state/vsys/`, and a file only the home default holds stays in use while a variable points elsewhere. `src/config/xdg.test.ts` checks each variable set, unset, empty and relative, and each place the file can be; `src/config/config.test.ts` checks the three resolved paths for those cases, that a moved variable keeps an existing install's saved settings and state directory, and that a save after the state directory moves pins no state path; `src/runtime.test.ts` checks that a save writes where the settings path resolves at save time.
20. The Settings scrub reports row shows the install line while no report directory exists, and the copy key copies it there, a row `capabilityOffer()` answers copies its line, and a row that offers no line copies nothing. `src/ui/settings-screen.test.tsx` checks each.
21. The Settings row naming the settings file shows the path vsys actually resolved, whether the XDG default or an explicit `--config` override, and its detail carries that path whole even where the row itself cuts it, as the shared cut-row rule requires. `src/ui/settings-screen.test.tsx` checks both.
22. The settings path shown on every sample is the same resolver call a save makes, so a reader who moves the settings file mid-session sees the new path before the next save, never the one from the sample before. `src/runtime.test.ts` checks that the frame's path follows the resolver on the next sample with no save in between; `src/ui/screen.test.tsx` checks that `mountScreen`'s `update()` call, not its mount-time actions, decides the path the Settings screen shows.
23. A save publishes its resolved settings path to the screen before it writes, so a reader who moves the settings file and saves before the next sample sees the path the save is writing to, not the one the sample before it showed. `src/runtime.test.ts` checks a save that follows a file move with no sample in between.
