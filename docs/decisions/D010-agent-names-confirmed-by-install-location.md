# D010: Confirm agent names by install location

[← Decision Index](INDEX.md)

**Date**: 2026-10-01

**Status**: Active

**Research**: VSY-41

**Context**: The dashboard called a process an agent when its `comm`, its executable's basename or an interpreter's script basename equalled a configured name. Generic names such as `pi` and machine-local names such as `dsh` then matched anyone's program or script. Outside the agent slice, each match raised the escaped-agent card.

**Decision**: A configured name is a candidate. Each tool entry in the agent-tool data lists where its installs put it: `paths` fragments, whole `executables` paths, and its `mise` install directories. An executable name matches only where the process's executable lies in one of its tool's install locations or is a bundled CLI engine. A script basename matches only where the script, with its links resolved, lies in one. In the warden, a bundled-CLI-engine, executables-exact or mise-anchored match holds even under a desktop prefix: `is_desktop` itself excludes such an executable before the agent check runs, so neither `Proc.is_agent` nor `Proc.is_named_agent` vetoes it, and planning does not skip it as a desktop app. The dashboard's own desktop rule carves out only the bundled CLI engine. A Node or Bun process whose program replaced its title with the tool's name also matches, because the title change erases the script path. An entry with no install location matches by executable name alone, and never by script. Every shipped entry names an install location, and an overlay entry with a shipped name adds locations to that tool. A path vsys could not read keeps the name. A configured name the locations reject is recorded on the process as `unconfirmedTool`.

**Rationale**:

- An install location is a second signal that a coincidental name does not carry: an unrelated `/usr/bin/dsh` or `~/bin/pi.sh` lies in no agent's package or version directory.
- Settings edits names only. Requiring a location for a reader's own name would make every Settings addition do nothing, so a name with no location stays the reader's claim.
- The `AGENT_CONFINE=1` launcher marker was rejected as a signal. Every descendant of a confined launch inherits it, so it would vouch for any `dsh` or `pi.sh` an agent runs.
- Recording the rejected name keeps a missed install layout visible in the snapshot instead of silent.

**Revisit When**: An agent CLI ships an install layout that no path fragment or executable path can describe.

**Verification**: `src/collect/collector.test.ts` tables each shipped CLI's install shapes, scripts and programs that only share a name, unreadable paths, an overlay that extends a shipped tool, and the owner's machine. `src/config/agent-tools.test.ts` fails if a shipped tool names no install location. The warden, which moves a confirmed match automatically, applies a narrower comm rule than the dashboard's display-only match: it never reads a tool's `paths` fragments, because a bare substring of one is forgeable by any same-uid process writing under its own directory, and confirms only an executable anchored under the tool's mise install directory, an exact configured executable path, or a bundled CLI engine under a desktop prefix that is a real install location. A tool whose only location is a `paths` fragment, such as a machine overlay entry, still names a location, so the warden does not trust its name alone the way it trusts a name with no location: it confirms that tool only as a bundled CLI engine. A desktop prefix under `/tmp` never confirms a bundled CLI, because `/tmp` is world-writable on every Linux target, including under an AppImage's own mount point. A `/tmp`-prefixed executable that does not end in a bundled CLI suffix still reads as desktop through the warden's own `is_desktop` property, which keeps the full, unfiltered prefix list for that purpose; the bundled-CLI-shaped executable itself is neither agent nor desktop once its prefix is `/tmp`. `warden/agent_warden_test.py` tables a planted name outside every install location, a confirmed match by each anchored rule, a forged match attempted through each dropped or unanchored signal, a forged match attempted through a world-writable desktop prefix, an unreadable executable, and a name with no configured location. `test_paths_only_tool_needs_location_evidence` tables a tool located by `paths` alone, and `test_desktop_prefix_keeps_a_confirmed_install` an exact executable and a mise install under a desktop prefix; each has a mutant control.

This location confirmation gates only `Proc.is_agent`, the automatic move of an unmarked process into `agents.slice`. It never gates the move of an escaped launch, which carries `AGENT_CONFINE=1` and moves whatever its name (`test_escaped_launch_moves_an_unconfirmed_name`). It never gates orphan-reap protection. `Proc.is_named_agent` is the pre-decision comm-only name match, with no location confirmation, and `_is_orphan`/`scope_still_orphan` read it instead of `is_agent` to decide whether a scope holds a live agent. Claude's and codex's native, non-mise installs name their location only through `paths` in `data/agent-tools.json`, with no `executables` entry for either, so a genuine agent on one of those installs never satisfies this decision's location check: it fails `is_agent` but must still protect its scope, since D010 narrows only which processes the warden moves automatically, never which ones count as alive. `warden/agent_warden_test.py`'s `test_orphan_protection_uses_comm_only_name_match` and `test_orphan_protection_name_match_mutant_fails` enforce that a headless agent on such an install is not reaped once its launch shell exits.
